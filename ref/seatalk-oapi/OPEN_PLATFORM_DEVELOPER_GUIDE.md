# SOP Open Platform Developer Integration Guide

This guide is based on the current implementations of [`seatalk-oapi-sdk-go`](./seatalk-oapi-sdk-go) and [`seatalk-oapi-sdk-py`](./seatalk-oapi-sdk-py). It is intended for SOP open platform developers who need to integrate with the `seatalk open platform` WebSocket protocol.

Chinese version: [`OPEN_PLATFORM_DEVELOPER_GUIDE_cn.md`](./OPEN_PLATFORM_DEVELOPER_GUIDE_cn.md)

## 1. What You Can Build With These SDKs

Both SDKs wrap the same developer bot WebSocket protocol and provide the same core capabilities:

- Send `register` with `app_id` / `app_secret`
- Receive a session `token` after successful registration
- Receive platform-pushed `event` messages continuously
- Automatically send `ack` after an event with `callback_id` is handled successfully
- Send application-level `ping` while the connection is alive, and consume `pong` silently
- Support default envelope logging, custom envelope logging, and custom invalid-frame logging
- Support generic event handling and typed event handlers

The current default WebSocket URL constant is `wss://ws-openapi.haiserve.com/ws/bot`.

## 2. SDK Directories And Language Choice

### Go SDK

- Path: [`seatalk-oapi-sdk-go`](./seatalk-oapi-sdk-go)
- Main types:
  - `Client`
  - `EventDispatcher`
  - `Envelope`
  - Typed event structs

### Python SDK

- Path: [`seatalk-oapi-sdk-py`](./seatalk-oapi-sdk-py)
- Characteristics:
  - Pure standard-library implementation
  - No third-party WebSocket package required
  - API naming is aligned with the Go SDK where practical

If your bot service is already written in Go, prefer the Go SDK. If you want to validate the integration quickly, build a lightweight callback service, or consume events from scripts, the Python SDK is convenient.

## 3. Before You Start

Make sure you have:

- The `app_id` assigned by the open platform
- The `app_secret` assigned by the open platform
- The WebSocket endpoint for your target environment, defaulting to `wss://ws-openapi.haiserve.com/ws/bot`

Clarify two questions before implementation:

1. Which event types do you need to consume?
2. Should the platform retry when your business processing fails?

The second point is important. Automatic `ack` only happens after event processing succeeds:

- Go: the handler returns `nil`
- Python: the handler returns normally without raising an exception

If your business processing fails, do not swallow the error. Otherwise the SDK will treat the event as successfully processed and confirm it automatically.

## 4. Protocol Interaction Model

The overall flow is:

1. The client establishes a WebSocket connection
2. The client sends `register`
3. The platform returns the `register` response
4. After successful registration, the SDK stores the `token`
5. The platform continuously pushes `event` messages
6. The SDK dispatches events to a generic handler or typed handlers
7. If the event contains `callback_id` and the handler succeeds, the SDK automatically sends `ack`
8. The SDK continuously sends `ping` according to the heartbeat interval
9. The platform returns `pong`
10. If the platform actively disconnects the client, it may send `kick`

### Supported Commands

- `register`
- `ack`
- `ping`
- `pong`
- `kick`
- `event`

### Request And Session IDs

Every outgoing command uses the shared envelope `header`.

- `rid`: a request ID generated by the SDK before sending a request, unless the caller has already provided one
- `sid`: a session ID returned by the platform in the successful `register` response header

When a logger is configured, both SDKs log sent commands with the generated `rid`, for example `sent ping command rid=<rid>`.

### What You Receive After Successful Registration

After `register` succeeds, the SDK returns:

- `app_id`
- `token`
- `sid`
- `heartbeat_interval`
- `heartbeat_timeout`

Both SDKs use `heartbeat_interval` as the preferred heartbeat interval. If the server does not return it, the SDK falls back to the local default of `15s`. `heartbeat_timeout` is parsed and exposed in the registration result, but the SDK currently does not perform additional timeout control based on it.

## 5. Quick Start

### Minimal Go Example

```go
package main

import (
	"context"
	"log"

	seatalkoapisdk "git.garena.com/seatalk/seatalk-oapi-sdk-go"
)

func main() {
	dispatcher := seatalkoapisdk.NewEventDispatcher().
		OnMessageFromBotSubscriber(func(ctx context.Context, event *seatalkoapisdk.MessageFromBotSubscriberEvent) error {
			if event.Event.Message.Tag == seatalkoapisdk.MessageTagText && event.Event.Message.Text != nil {
				log.Printf("subscriber text=%s", event.Event.Message.Text.Content)
			}
			return nil
		})

	client := seatalkoapisdk.NewClient(
		"your-app-id",
		"your-app-secret",
		seatalkoapisdk.WithWebSocketURL("wss://your-websocket-endpoint"),
		seatalkoapisdk.WithEventDispatcher(dispatcher),
	)
	defer client.Close()

	if err := client.Run(context.Background()); err != nil {
		log.Fatal(err)
	}
}
```

### Minimal Python Example

```python
from seatalk_oapi_sdk import Client, EventDispatcher, MESSAGE_TAG_TEXT


def handle_message(event):
    message = event.event.message
    if message.tag == MESSAGE_TAG_TEXT and message.text is not None:
        print("subscriber text:", message.text.content)


dispatcher = EventDispatcher().on_message_from_bot_subscriber(handle_message)

client = Client(
    app_id="your-app-id",
    app_secret="your-app-secret",
    ws_url="wss://your-websocket-endpoint",
    dispatcher=dispatcher,
)

try:
    client.run()
finally:
    client.close()
```

## 7. Supported Event Types

Both SDKs currently support the following 8 typed events:

| Event Type | Description | Common Key Fields |
| --- | --- | --- |
| `user_enter_chatroom_with_bot` | A user enters a bot chatroom | `seatalk_id` `employee_code` `email` |
| `message_from_bot_subscriber` | A subscriber sends a message to the bot | `seatalk_id` `message.tag` `message.text/image/file/video` |
| `new_mentioned_message_received_from_group_chat` | The bot is mentioned in a group chat | `group_id` `message.sender` `message.text.plain_text` |
| `interactive_message_click` | A user clicks an interactive message | `message_id` `value` `seatalk_id` `group_id` `thread_id` |
| `new_message_received_from_thread` | A new message is received in a thread | `group_id` `message.thread_id` `message.tag` |
| `bot_added_to_group_chat` | The bot is added to a group chat | `group.group_id` `group.group_name` `inviter` |
| `bot_removed_from_group_chat` | The bot is removed from a group chat | `group_id` `remover` |
| `group_chat_converted_to_external_group` | A group chat is converted to an external group | `group_id` `operator` |

Event details: https://open.seatalk.io/docs/list-of-events

## 8. Message Body Field Notes

### 8.1 `message_from_bot_subscriber`

The `message` object currently supports these `tag` values:

- `text`
- `image`
- `file`
- `video`
- `combined_forwarded_chat_history`

Field mapping:

- `text` maps to `message.text.content`
- `image` maps to `message.image.content`
- `file` maps to `message.file.content` and `message.file.filename`
- `video` maps to `message.video.content`

The `combined_forwarded_chat_history` constant is exposed in both SDKs, but the typed model does not currently provide a dedicated field for it. If you need to handle this message type, first inspect the raw data through the default envelope log, then decide whether to parse it through the generic event path.

### 8.2 `new_mentioned_message_received_from_group_chat`

Common text-message fields:

- `message.text.plain_text`
- `message.text.mentioned_list`
- `message.sender`
- `message.thread_id`

### 8.3 `new_message_received_from_thread`

Common thread-message fields:

- `message.thread_id`
- `message.tag`
- `message.text.plain_text`
- `message.mentioned_list`

## 9. Handler Registration

### Go

The Go SDK registers handlers through a chainable API:

```go
dispatcher := seatalkoapisdk.NewEventDispatcher().
	OnMessageFromBotSubscriber(handleSubscriberMessage).
	OnInteractiveMessageClick(handleInteractiveClick).
	OnKick(handleKick).
	OnEnvelope(handleEnvelope).
	OnInvalidFrame(handleInvalidFrame)
```

You can register:

- `OnEvent`: generic event handling
- Typed handlers: structured event handling
- `OnEnvelope`: intercept every valid envelope
- `OnInvalidFrame`: handle invalid JSON frames
- `OnKick`: handle platform kick-off messages

### Python

The Python SDK provides both snake_case methods and Go-style alias methods:

```python
dispatcher = (
    EventDispatcher()
    .on_message_from_bot_subscriber(handle_subscriber_message)
    .on_interactive_message_click(handle_interactive_click)
    .on_kick(handle_kick)
    .on_envelope(handle_envelope)
    .on_invalid_frame(handle_invalid_frame)
)
```

If you want to stay aligned with Go documentation or existing conventions, you can also use alias methods such as `OnMessageFromBotSubscriber`.

## 10. Automatic Ack

This is one of the easiest details to miss, and one of the most important.

Automatic `ack` is triggered only when:

- The incoming command is `event`
- The event header contains `callback_id`
- At least one handler actually handled the event
- Processing completed without an error

This means:

- Registering only `OnEnvelope` / `on_envelope` does not trigger automatic `ack`
- Printing logs without registering a generic event handler or typed handler does not trigger automatic `ack`
- If you want to control confirmation timing yourself, use the manual flow and call `Ack(callbackID)`

## 11. Connection And Lifecycle APIs

The core APIs of both SDKs are aligned:

| Capability | Go | Python | Description |
| --- | --- | --- | --- |
| Connect and register | `Connect(ctx)` | `connect()` | Returns registration result and token |
| Start listening | `Start(ctx)` | `start()` | Reads messages continuously and sends heartbeat |
| Run in one step | `Run(ctx)` | `run()` | Performs connect + start internally |
| Manual ack | `Ack(ctx, callbackID)` | `ack(callback_id)` | Sends `ack` |
| Manual heartbeat | `Ping(ctx)` | `ping()` | Sends application-level `ping` |
| Close connection | `Close()` | `close()` | Closes the WebSocket |

If you want the quickest integration path, prefer `Run` / `run`.

If you need to separately manage "return token after registration", "start consuming events", and "graceful shutdown", use `Connect + Start + Close`.

## 12. Configuration

### Go `ClientOption`

The Go SDK supports:

- `WithWebSocketURL`
- `WithDialer`
- `WithRequestHeader`
- `WithHandshakeTimeout`
- `WithWriteTimeout`
- `WithPingInterval`
- `WithReadLimit`
- `WithEventDispatcher`
- `WithLogger`

Common use cases:

- Add extra HTTP headers with `WithRequestHeader`
- Tune timeouts with `WithHandshakeTimeout` / `WithWriteTimeout`
- Set the local fallback heartbeat interval with `WithPingInterval`
- Print SDK send logs with generated `rid` through `WithLogger`

### Python `Client(...)`

The Python SDK constructor supports:

- `ws_url`
- `request_headers`
- `handshake_timeout`
- `write_timeout`
- `ping_interval`
- `read_limit`
- `dispatcher`
- `logger`

`request_headers` has the same purpose as Go's `WithRequestHeader`.

For `logger`:

- Both SDKs log sent application commands with `rid`, for example `sent ack command rid=<rid>`
- Python also logs some lower-level WebSocket debug information, such as received WebSocket `ping` frames
- For received application envelopes and invalid frames, prefer `OnEnvelope` / `on_envelope` and `OnInvalidFrame` / `on_invalid_frame`

## 13. Error Handling Suggestions

Both SDKs explicitly distinguish several common error types:

- Missing credentials: empty `app_id` / `app_secret`
- Duplicate connection: calling `connect` when already connected
- Sending while not connected
- Calling `ack` / `ping` before successful registration
- Platform rejects `register`: `RegisterError`
- Platform kicks the client offline: `KickError`

Recommended practices:

1. Log `RegisterError` separately, so credential/configuration errors are easier to distinguish from network errors
2. Log the platform-returned `message` for `KickError`
3. Propagate real business errors from handlers to avoid confirming failed events
4. Always call `Close` / `close` during graceful shutdown

## 15. A Safe Integration Sequence

A practical rollout sequence is:

1. Use `basic_client` to connect to the environment and confirm that `register` succeeds
2. Inspect the default envelope output and confirm which `event_type` values you actually receive
3. Register typed handlers only for the first batch of required events
4. Add logging and field validation in handlers before connecting real business logic
5. Replace envelope / invalid-frame logging with your own logging solution when the flow is stable

This separates protocol issues, field issues, and business issues, which makes troubleshooting faster.

## 16. Closing Notes

If you only need to get an SOP bot connected quickly, start from the typed handler example. If you are not sure which fields the platform will push, run `basic_client` first and inspect raw envelopes.

This document describes the capabilities currently implemented in the Go/Python SDKs in this repository. If the open platform adds new event types or message structures later, update both the SDK typed models and this integration guide.
